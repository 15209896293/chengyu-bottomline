## 一、项目全貌

### 1.1 基本信息

- **项目名称**：城域底线——城市生命线底线债务诊断
- **比赛**：中国大学生计算机设计大赛（4C）· 大数据实践赛（自主命题）
- **国赛形式**：10分钟汇报 + 10分钟答辩
- **提交材料**：设计报告(PDF) + 源码及部署包 + Web应用展示视频 + 自建数据集
- **一句话定位**：用大数据算出城市生命线"在哪崩、为什么崩、怎么延缓崩"

### 1.2 核心立意

城市发展留下了看不见的**底线债务**：老城区道路老化、新城区医院稀疏、新老城交界处规划脱节。这些债平时看不见，但灾害来时会集中爆发。

**地震不是项目主题，地震是检验这些债务的压力测试手段。** 就像体检时跑步测心脏——我们用地震推演来暴露城市生命线的结构性脆弱。

### 1.3 三个创新点

| 创新点 | 别人怎么做 | 我们怎么做 |
|--------|-----------|-----------|
| 跨系统拓扑依赖建模 | 各系统独立评估 | 建模4系统间依赖关系，计算崩溃传播 |
| 崩溃临界点识别 | 算"损失多少亿" | 算"什么时候扛不住"（M5.5医疗崩） |
| 底线债务诊断 | 定性说"有风险" | 量化城市发展遗留的结构性脆弱 |

### 1.4 方法论：五步算法链

1. **压力施加**：地震烈度场 → 500m网格级破坏力计算
2. **单系统失能**：路网阻断 → 医院可达性（NetworkX Dijkstra）→ 医疗功能率
3. **跨系统依赖**：医疗对交通的依赖度 = 依赖受损路网的医院占比
4. **崩溃传播**：交通崩 → 沿依赖边传染给医疗 → 医疗崩 → 传染给避难
5. **临界点识别**：扫描M5.0-M7.5，找哪个系统在哪个震级先崩

### 1.5 核心发现（关键数据）

| 发现 | 数据 |
|------|------|
| 医疗崩溃震级 | M5.5（功能率26.8% < 30%阈值） |
| 崩溃原因 | 老城区路窄+老化率43%，44%医院不可达 |
| 救援崩溃震级 | M6.0（功能率37.7%） |
| 避难崩溃震级 | M7.0（功能率43.8%） |
| 策略A效果 | 加固10条关键路段 → 阈值推移+0.5M |
| 策略C效果 | A+B组合 → 医疗功能率0.268→0.443，最优 |
| 暴露人口(M5.5) | 531万 |
| 经济损失(M5.5) | ¥346亿 |
| 韧性指数(M5.5) | 0.616（中等韧性） |

## 三、技术决策历史（踩过的坑和选型理由）

### 3.1 为什么是深色科技风不是浅色

- 用户原话："浅色全白太单调，还没有原版好看"
- 最终确认：深蓝黑背景#0A1320 + 青色主色#00D4FF
- 状态色：success #34D399 / warning #FBBF24 / error #F87171 / orange #FB923C

### 3.2 为什么是4个模式不是7页

- 最初设计7页（4层叙事结构），被用户否决
- 用户原话："7独立页面信息分页堆叠、地图仅作配图，本质是换皮PPT"
- 最终确认：1个统一工作台 + 4个叙事模式，地图始终在中央

### 3.3 为什么用Leaflet不用Mapbox/MapLibre

- Leaflet轻量开源，AI生成代码成熟
- 高德地图API瓦片国内访问稳定，浅色底图风格
- 不需要Mapbox的3D和矢量瓦片能力

### 3.4 为什么用Chart.js不用ECharts

- 样图阶段用Chart.js验证通过
- 项目计划书中提到ECharts，但实际样图全部用Chart.js
- **决策**：前端实现时统一用Chart.js（与样图一致，减少迁移成本）
- 如果新窗口认为ECharts更适合，可以替换，但需要保持视觉一致

### 3.5 坐标系约定

- **地理坐标**：EPSG:4490（CGCS2000）
- **投影计算**：EPSG:4527（高斯-克吕格3度带）
- GeoJSON文件统一用4490
- 距离/面积计算用4527投影

### 3.6 Python环境

- Conda环境名：`zhenmai`
- Python 3.10
- 运行命令：`conda run -n zhenmai python [脚本路径]`
- GDAL/PROJ路径：`F:/anaconda/envs/zhenmai/Library/share`
