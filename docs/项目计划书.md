## 一、项目概述

### 1.1 项目名称

**城域底线——城市生命线底线债务诊断**

### 1.2 一句话定位

用大数据算出城市生命线"在哪崩、为什么崩、怎么延缓崩"——填补政府跨系统评估的盲区。

### 1.3 项目内涵

城市化快速推进，我们建了很多新楼、修了很多新路，但留下了看不见的脆弱。这些脆弱平时不被察觉，但灾害来时会集中爆发。每一个"崩溃临界点"背后，是无数普通人的生命安全。我们不是在算数字，而是在算"城市对谁不负责"。

城市的底线，就是城市对居民生命安全的承诺。底线债务就是这个承诺被欠下了。

**债务有具体的承受者。** 老城区路窄没拓宽，老城区的居民用生命还；新城区建了宽马路但没配够医院，新城区的居民以为自己安全其实不是。规划决策留下的代价，不由决策者承担，而由住在那里的人承担。

**我们算的不只是"城市对谁不负责"，更是"谁的债让谁还"。** 空间错配不只是风险和资源的不匹配，是城市发展中资源分配的不正义——脆弱性被无声地转移给了最没有能力抵抗的人。

**这才是"底线"的真正含义：** 不只是技术阈值（如医疗功能率27%），是城市对每个普通人生命安全的承诺底线。底线被突破，不是数字变了，是承诺被违背了。

### 1.4 核心立意

城市发展留下了看不见的**底线债务**：老城区道路老化、新城区医院稀疏、新老城交界处规划脱节。这些债平时看不见，城市运转正常，但一旦承受压力（地震、暴雨、疫情）就还不上了。

**地震不是项目的主题，地震是检验这些债务的手段。** 就像体检时的压力测试——你平时心率正常，但跑个步才知道心脏有没有问题。

- **比赛**：中国大学生计算机设计大赛（4C）· 大数据应用赛 · 大数据实践赛（自主命题，自带数据集）

## 二、问题分析

### 2.1 我们发现了什么问题

合肥看起来正常，但数据揭示它有隐藏的脆弱性：

- **空间错配**：地震高风险区（断裂带沿线）恰恰是资源稀疏区
- **新老城债务**：老城区医院密集但路窄老化，新城区路宽但医院稀疏
- **跨系统盲区**：交通局知道哪条路会断，但不知道断了之后哪几家医院失救；卫健委知道医院可达性，但不知道救援系统崩了之后医疗会怎么被拖垮

### 2.2 为什么这个问题重要

- 城市化快速推进留下了规划债，这些债在自然灾害面前会集中暴露
- 广西暴雨、郑州暴雨等事件已证明：城市脆弱性不是单点问题，是系统级问题
- 政府部门按系统割裂管理，没有"跨系统依赖"的评估工具

### 2.3 为什么这个视角有价值且尚未被实现

**不是"别人做不了"，是"这个视角还没有被数据化地做过"。**

- 政府做灾害评估，关注的是"损失多少亿"——结果是数字
- 科研机构做地震研究，关注的是"地震危险性"——结果是概率
- 没有人从"**城市发展留下了什么债、这些债怎么爆发、怎么还**"这个视角，用数据做诊断

这个视角把城市规划的议题、复杂网络的方法、大数据的技术结合在一个交叉点上，这个交叉点还没人站过。

**比赛不要求证明垄断性，要求的是创新性。** 创新性在于视角，不在于"别人做不到"。

### 2.4 能力边界：诊断而非解决方案

**我们做诊断工具，不做解决方案。**

- 不替政府做决策，而是给他们一个用数据看清楚问题的工具
- 类比：我们不是开药方的医生，而是做CT扫描的设备
- 这符合大数据实践赛要求："数据驱动决策支持"，不是"数据驱动决策"

## 三、方法论

### 3.1 算什么

**算的不是单系统损失，是系统间的依赖关系和崩溃传播。**

四个城市生命线系统：
1. **交通系统** — 路网连通度
2. **医疗系统** — 医院可达性
3. **救援系统** — 消防站可达性
4. **避难系统** — 避难容量/需转移人口

### 3.2 在哪算

| 计算单元 | 算什么 | 数据 |
|---------|--------|------|
| 500m网格 | 烈度场、人口暴露、GDP暴露 | 已有46K网格 |
| 路段 | 阻断概率、连通度 | 已有58K路段 |
| 系统节点 | 医疗/救援/交通/避难的功能率 | 已有数据 |
| **拓扑边** | **系统间依赖关系**（医疗依赖交通的比例） | **要新建** |

关键创新在第四行——把四个系统建成有向依赖图，计算崩溃怎么在系统间传播。

### 3.3 怎么算——五步算法链

1. **压力施加**：地震烈度场 → 网格级破坏力计算
2. **单系统失能**：路网阻断 → 医院可达性（NetworkX Dijkstra）→ 医疗功能率
3. **跨系统依赖**：医疗对交通的依赖度 = 依赖受损路网的医院占比
4. **崩溃传播**：交通崩 → 沿依赖边传染给医疗 → 医疗崩 → 传染给避难
5. **临界点识别**：扫描震级，找哪个系统在哪个震级先崩，定位"城市底线"

### 3.4 为什么地震是入口

地震能**同时**冲击所有系统（道路、医院、消防、避难所），是检验跨系统依赖的最佳压力源。暴雨只冲击排水和交通，疫情只冲击医疗，只有地震是全系统压力测试。

## 四、创新点

### 4.1 三个创新点

| 创新点 | 别人怎么做 | 我们怎么做 |
|--------|-----------|-----------|
| **跨系统拓扑依赖建模** | 各系统独立评估 | 建模系统间依赖关系，计算崩溃传播 |
| **崩溃临界点识别** | 算"损失多少" | 算"什么时候扛不住" |
| **底线债务诊断** | 定性说"有风险" | 量化城市发展遗留的结构性脆弱 |

### 4.2 新形态大数据

不是传统"数据量大、来源多"的大数据。是**数据驱动的系统认知**：

| 传统大数据 | 我们的新形态 |
|-----------|-------------|
| 统计相关性 | 因果穿透（拓扑依赖链） |
| 指标堆砌 | 系统崩溃临界点识别 |
| 描述性分析 | 压力测试推演 |
| 单系统优化 | 跨系统级联失效建模 |
| 静态报告 | 交互式诊断工具 |

**核心创新：用大数据把城市理解为一个复杂系统，而不是一堆孤立指标的集合。**

**升级方向**：跨系统依赖传播

- 医疗功能率 → 影响避难功能率（避难依赖医疗转运伤员）
- 救援功能率 → 影响避难功能率（危险源失控）

实现步骤：
1. 从可达性矩阵推导系统间依赖权重
2. 改造崩溃判定：从孤立阈值改为传播模型
3. 重新生成预计算JSON

## 六、展现设计

### 6.1 展现形态

**一个网页。主视图是合肥4区4县的地图。**

地图大屏方向没错，深度在于让地图讲出别人讲不出的故事。

### 6.2 四个展现层次

**第一层：发现债务**
打开网页，先看到合肥的城市空间格局。地图上能看出：老城区医院密但路窄，新城区路宽但医院少，新老城交界处资源断层。这一层回答"城市欠了什么债"。

**第二层：压力施放，债务暴露**
施加地震压力，看哪些债先还不上了。不是简单地"医疗崩了"，而是"老城区因为路窄先断了，导致密集的医院反而先失救"——这种反直觉的发现才有深度。

**第三层：穿透根源**
为什么这里先崩？点开一个崩溃区域，看到的是：这个区老城比例高、路网老化、消防站覆盖不足——这是规划历史遗留的债，不是地震本身的问题。

**第四层：偿还策略**
加固哪些路、在哪里增建消防站，能把底线推高。但也要展示：有些债短期还不上（老城区没法拆了重建），只能靠区域协调来补。

### 6.3 信息节奏原则

- 不是一次全展示，按"正常→施压→崩溃→因果→解决"的顺序展开
- 地图上同一时刻只突出一个重点
- 用户跟着节奏理解整个发现
- 临界点不是被告知的，是用户自己撞上的

### 6.4 视觉风格

- 深色科技风：深蓝黑背景 #0A1320 + 青色主色 #00D4FF
- 卡片层 #0F1A2B / 内嵌面板 #16243C / 边框 #1C2B43
- 语义化配色：success #34D399（正常）/ warning #FBBF24（警戒）/ error #F87171（崩溃）/ orange #FB923C（承压）
- 信息密度优先，每寸屏幕都承载数据
- 字体：Inter + Noto Sans SC + JetBrains Mono
- 7个模式共享统一AppShell（TopBar + 56px窄侧边栏 + KpiBar），地图始终在中央

## 七、开发计划

### 7.1 开发策略：算法与前端同步推进

**核心原则：算法不单独成阶段，而是和前端同步推进，以"前端需要什么数据"为终点反推算法输出什么。**

之前的问题是：把算法当成独立任务先做完，做完之后前端发现数据格式对不上，又要回头改算法，改了又影响前端。

**新的做法：**
1. 先明确前端要用的JSON结构（哪些字段、什么格式）
2. 算法升级直接产出这个JSON结构，不经过CSV中转
3. 每次算法改动后立即重新生成JSON，前端立即用新数据验证
4. 算法和前端是同一个迭代循环，不是两个阶段

**一句话：算法不是"先做完再交接"，而是"每改一步就对接一步"。**

### 7.2 阶段划分

**覆盖系统**：建筑（群）、交通（道路/地铁）、供水、排水、燃气、供热、供电、通信、医疗——9大类城市工程系统

**核心能力**：
- 城市地震动场智能快速模拟
- 建（构）筑物和城市工程系统**定量抗震韧性评价**
- 城市工程系统易损性数据库扩展、二次开发、GIS可视化展示

**标准体系**：牵头编制我国首部《城市工程系统抗震韧性评价导则》，形成"国家+协会"标准体系 [$TRAE_REF](https://news.hit.edu.cn/2025/1126/c11819a240140/page.htm)

**应用案例**：北京山区平急两用高速公路、广东省电网抗灾韧性、上海典型社区建筑群

**成果链条**：理论→方法→技术→规范→软件（全链条）

**团队规模**：院士1人 + 国家杰青1人 + 国家青年人才3人 + 研究生70余人 + 50余项国家省部级项目

### 11.2 他们为什么能做软件

| 维度 | 哈工大 | 我们 |
|------|--------|------|
| **团队能力** | 院士+杰青+70研究生，土木工程+人工智能交叉学科 | 一名学生 + AI agent |
| **数据基础** | 建筑级结构数据（层数、抗震等级、材料），来自政府合作 | 开放POI + OSM路网，无结构级数据 |
| **标准依据** | 自己编制了国标和导则，软件是标准的落地实现 | 无标准可依，是方法论创新 |

**结论：他们做软件是因为他们有工程数据、标准体系、专业团队，做的是"标准落地工具"。我们做网页是因为我们用开放数据、创新视角、交互叙事，做的是"认知诊断工具"。形态不同是因为定位不同，不是能力高低。**

### 11.3 哈工大的呈现方式

哈工大平台是**专业工程软件**形态：

1. **界面**：GIS桌面软件风格，类似ArcGIS——左侧功能树（建筑/交通/供水/...各系统模块），中间地图画布，右侧属性面板和评价结果
2. **交互**：工程师选一个系统→输入参数→运行评价→输出韧性评分（数值+等级标签）→GIS上着色展示
3. **输出**：每个系统得到一个韧性等级（如"Ⅰ级/Ⅱ级/Ⅲ级"），按行政区划汇总
4. **用户路径**：专业人员操作→逐系统评估→生成报告→供决策参考
5. **信息组织**：按工程系统分类组织（建筑一组、交通一组、供水一组...），各系统独立评估

### 11.4 核心差异：不是竞争，是互补

| 对比维度 | 哈工大平台 | 我们的项目 |
|---------|-----------|-----------|
| **核心问题** | 每个系统韧不韧？ | 系统之间怎么互相拖垮？ |
| **评估对象** | 单系统韧性评分 | 跨系统崩溃传播路径 |
| **方法论** | 结构工程+韧性理论 | 复杂网络+压力测试 |
| **数据粒度** | 建筑级（单栋楼抗震性能） | 系统级（路网-医院-消防的拓扑关系） |
| **关键输出** | 韧性等级（Ⅰ/Ⅱ/Ⅲ级） | 崩溃临界点 + 级联传播链 |
| **空间视角** | 按系统分别着色 | 崩溃在空间上波浪式扩散 |
| **时间视角** | 静态评分（震前评估一次） | 动态推演（拖震级看崩溃扩散） |
| **交互方式** | 参数输入→计算→出报告 | 滑块推演→自己撞上临界点 |
| **创新焦点** | 精确（把韧性算准） | 洞察（看见跨系统依赖） |
| **盲区填补** | 单系统评估工具缺失 | 跨系统依赖分析工具缺失 |

**一句话总结差异**：他们回答"每个系统够不够韧"，我们回答"系统之间怎么互相拖垮"。这两个问题不重叠，是互补关系。

### 11.5 原创性保证

**我们不做哈工大已经做的事**：
- 不做单系统韧性评分（他们有国标+工程数据，我们没有）
- 不做建筑级结构分析（我们没有建筑层数、抗震等级数据）
- 不做"标准落地工具"（我们没有标准可落地）

**我们做哈工大没做的事**：
- 跨系统拓扑依赖建模（他们的平台是各系统独立评估，没有系统间依赖传播）
- 崩溃临界点识别（他们算韧性评分，不算"什么时候崩"）
- 压力测试推演（他们是静态评估，我们是动态推演）
- 城市底线债务诊断视角（他们做工程技术评估，我们做城市发展模式诊断）

**借鉴他们的地方**：
- 多系统覆盖的思路（他们覆盖9系统，我们覆盖4系统，思路一致但系统间建模方式不同）
- GIS可视化展示（他们用GIS着色，我们也用地图，但交互逻辑不同）
- 理论-方法-技术-应用的成果链条结构（我们借鉴这个结构组织项目）

### 12.5 与哈工大展现方式的本质区别

| 展现维度 | 哈工大（专业软件） | 我们（交互工作台） |
|---------|------------------|----------------|
| **信息组织** | 按工程系统分类（建筑/交通/供水...） | 按诊断逻辑展开（格局→临界→级联→韧性→沙盘→验证） |
| **用户角色** | 操作者：输入参数→得结果 | 分析者：切换模式→拖动滑块→自己发现 |
| **核心体验** | "我算出了韧性评分" | "我自己撞上了崩溃临界点" |
| **地图作用** | 展示评估结果（着色） | 诊断主体（状态随推演实时变化） |
| **信息节奏** | 一次性展示所有系统 | 7模式渐进深入，每模式聚焦一个诊断维度 |
| **结论传达** | 报告中写明韧性等级 | 用户通过交互自己得出结论 |

### 12.6 设计原则

1. **地图是主体，不是配角**：地图占屏幕中央主视觉区，7个模式中3个以地图为核心
2. **信息密度优先**：每寸屏幕都承载数据，三栏布局充分利用空间，不留装饰性空白
3. **交互即发现**：临界点不是被告知的，是用户拖震级滑块自己撞上的
4. **深色科技风**：#0A1320深蓝黑背景 + #00D4FF青色主色，语义化配色（绿/黄/红/橙）传达系统状态
5. **模式间共享骨架**：AppShell+TopBar+Sidebar+KpiBar统一不变，切换模式只更新主内容区，保持操作连续性
6. **数据透明**：KpiBar始终展示关键指标，底部图表展示算法依据，让评委信任数据
