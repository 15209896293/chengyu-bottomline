## 一、被否决的方案

### 1.1 单页图表大屏（第一版，已完成但被否决）

**问题：**
- 太简单，只有一页，堆砌了 11 个图表
- 丢失了旧版 app.py 的核心功能（路段修复推演、决策矩阵、急救枢纽推荐、延误矩阵、盲区分析）
- 核心创新点（崩溃临界点 M5.5）埋没在小图表里，完全没有突出
- 本质是"数据可视化看板"，不是项目成果展示

### 1.2 多页叙事式图表大屏（第二版方案，被否决）

**方案：** 6 页叙事流（总览→空间错配→脆弱性→崩溃临界点→防治推演→韧性评估）

**被否决的原因：**
- 换成多页本质上还是在做图表展示，只是组织方式变了
- 图表展示（无论单页多页）的本质是"看我们算了什么"
- 项目的核心价值不是"算了很多数据"，而是"崩溃临界点"这个方法论
- 做图表堆砌，评委看到的是"一个数据看板"，而不是"一个能推演城市什么时候崩溃的工具"

### 1.3 否决的核心逻辑

| | 图表展示 | 项目应该做的 |
|---|---|---|
| 本质 | 展示计算结果 | 体验方法论 |
| 用户角色 | 观众 — 看你算的数据 | 操作者 — 自己推演发现 |
| 核心交互 | 切换震级看数字变 | 拖滑块看系统崩溃 |
| 临界点 | 告诉你"M5.5" | 你自己撞上 M5.5 |
| 评委感受 | "图表做得不错" | "这个工具有意思" |

## 二、确认的新方向：推演沙盘

### 2.1 核心理念

项目计划书的核心差异化：**"传统灾害分析算的是损失量，我们算的是城市功能崩溃的临界震级 — 从损失评估到底线识别的方法论升级"**

图表展示体现不了这个升级。推演沙盘才能 — 用户亲身体验"系统在某个震级突然崩溃"，这就是"底线识别"的具象化。

### 2.2 核心交互体验

用户拖动震级滑块 → 实时看到四个系统（医疗/救援/交通/避难）状态变化 → 在 M5.5 自己"撞上"医疗崩溃 → 警报触发 → 选择干预策略 → 看底线被推高。

**关键：临界点不是被告知的，是用户自己发现的。**

### 2.3 沙盘核心组件

1. 震级推演滑块（M5.0 ~ M7.5）
2. 四系统仪表（功能率 + 崩溃/警戒/正常状态）
3. 实时地图（烈度扩散 + 医院可达性 + 道路阻断）
4. 崩溃警报条
5. 策略推演对比（干预前 vs 干预后）

## 三、完整产品架构：四层结构（部分已确认，部分待规划）

### 3.1 第一层：推演沙盘 · 核心交互（已确认）

让用户**发现**临界点。

- 震级推演滑块 + 四系统仪表 + 实时地图
- 拖动震级 → 系统从绿变黄变红 → 在 M5.5 撞上医疗崩溃
- 占产品 70% 价值，是评委记住的东西

### 3.2 第二层：因果穿透 · 回答"为什么崩"（已确认缺失，待规划）

让用户**理解**为什么崩。发现崩溃后用户会立刻问"为什么"，当前方案回答不了。

**缺失组件：**
- **崩溃溯源链** — 点击"医疗崩溃"→ 展开因果链：断裂带震动 → 路段 #48130 阻断 → 蜀山区 12 家医院不可达 → 医疗功能率降至 27%。从结果穿透到根因。
- **空间崩溃热力图** — 城市不是整体崩溃。地图上展示哪些区域先失守 — 庐阳区在 M5.0 就红了，瑶海区 M5.5 才红。崩溃是空间渐进的。

### 3.3 第三层：崩溃传播 · 回答"然后呢"（已确认缺失，待规划）

让用户**看到**崩溃如何扩散。

**缺失组件：**
- **多米诺崩溃时序** — 四系统依次崩塌：M5.5 医疗先倒 → M6.0 救援跟着倒 → M7.5 避难最后倒。像多米诺骨牌，一个系统崩溃加速下一个系统崩溃。这是"级联失效"的可视化。
- **策略推演 + 底线推移** — 选择干预措施 → 临界点移动。加固 10 条路 → 底线 M5.5→M6.0。（prevention 数据已就绪）

### 3.4 第四层：方法论自证 · 回答"凭什么信你"（已确认缺失，待规划）

让评委**相信**这套方法。

**缺失组件：**
- **传统方法 vs 我们的方法** — 并列对比：传统"M6.0 损失 570 亿" / 我们"M5.5 系统就崩了"。同样的数据，不同维度的洞见。这是"从损失评估到底线识别"创新点的直接展示。
- **数据底牌 + 算法透明** — 46K 网格 · 58K 路段 · 426 家真实医院 · NetworkX 多源 Dijkstra · 烈度衰减模型。让评委看到数据规模和算法科学性，证明这不是拍脑袋。

## 四、四层结构的必要性

评委答辩时会问四个问题，四层结构逐一回答：

| 评委问题 | 对应层级 | 没有这层的后果 |
|---------|---------|--------------|
| "这个项目在做什么？" | 第一层：沙盘 | 只是一个数据看板 |
| "M5.5 为什么崩？" | 第二层：因果穿透 | 只能说"算出来的" |
| "崩了之后呢？" | 第三层：崩溃传播 | 只能说"就崩了" |
| "你的创新在哪？数据可靠吗？" | 第四层：方法论自证 | 只能说"报告里有写" |

**核心洞察：当前方案只展示了"结果"，没有展示"过程"和"方法"。**

- 结果 = M5.5 崩溃，27% — 这是数字
- 过程 = 路段#48130阻断 → 蜀山区12家医院失救 → 医疗系统崩溃 → 救援系统跟着崩 — 这是因果链
- 方法 = NetworkX图论 + 烈度衰减模型 + 四系统功能率阈值 — 这是科学性

评委 10 分钟答辩，记不住数字，但能记住"我点了一下，看到一条路断了导致12家医院失救，然后医疗崩了救援也跟着崩"这个体验。

## 六、技术突破：城市生命线拓扑崩塌引擎

### 6.1 当前算法的根本缺陷

当前崩溃临界点判断是**孤立的阈值判断**：
- 医疗 27% < 30% → 崩
- 救援 42% > 40% → 没崩
- 四系统各算各的，互不影响

**这不真实。** 现实中医疗崩了 → 伤员堆积 → 救援压力暴增 → 救援更快崩。一个系统崩塌会加速依赖它的系统崩塌。崩溃是**传播**的，不是孤立的。

### 6.2 拓扑崩塌引擎

把四系统建模为**有向依赖图**（网络），而非四个独立仪表：

```
交通 ──(医生/物资运输)──→ 医疗
交通 ──(消防车通行)──→ 救援
医疗 ──(伤员转运)──→ 避难
救援 ──(危险源管控)──→ 避难（次生灾害路径）
```

- 边的权重来自真实数据：医疗对交通的依赖度 = 可达医院中依赖该路网的比例
- 用复杂网络中心性算法找"崩塌关键节点" — 哪个系统崩了会拖垮最多下游

### 6.3 三个突破点

1. **拓扑依赖建模（方法论突破）** — 从孤立阈值到拓扑分析，建模崩溃如何在系统间传播
2. **蒙特卡洛概率崩塌（技术突破）** — 不是"崩/不崩"的二元判断，而是"78% 概率崩"。跑 N=1000 次模拟，加入不确定性，输出概率分布
3. **级联崩塌可视化（可视化突破）** — 拖动震级，看到崩塌在网络上传播：交通先红 → 沿依赖边传染给医疗 → 医疗红 → 传染给避难。像看病毒扩散

### 6.4 可行性

- 依赖关系：从已有的可达性矩阵推导（accessibility_M{X}.csv 已有医院→路网依赖）
- 蒙特卡洛：在现有 `generate_scenarios.py` 上加扰动循环
- 拓扑可视化：D3.js 力导向图

### 6.5 答辩话术

> "传统方法算损失量，我们算崩溃临界点；更进一步，我们建模崩溃如何在城市生命线系统间传播，用复杂网络理论找出城市的阿喀琉斯之踵，用蒙特卡洛给出概率而非确定性判断。这是从单点评估到系统拓扑分析的方法论飞跃。"

## 八、宏观突破方向（初步讨论）

### 8.1 核心问题：整个项目只算了"一张照片"

整个项目从头到尾就是在做一件事：算一次地震合肥会怎样。地震发生那一刻 → 道路断了、医院不可达、算出崩溃点 → 结束。这是一份数据分析作业，不是一个有深度的研究。

### 8.2 三个宏观突破维度

1. **时间维度：震后72小时演化** — 不只算"地震那一刻崩不崩"，算"震后1小时、6小时、24小时、72小时城市怎么逐步崩溃"。道路断了不是瞬间导致医院失能，是物资耗尽后才失能。这个时间差才是救援的黄金窗口。

2. **空间维度：崩溃在城市里怎么蔓延** — 不只算"全市崩了"，算"哪个区先崩、崩了怎么向相邻区域扩散"。庐阳区先红 → 伤员涌向蜀山区 → 蜀山区也被拖垮。崩溃在城市空间上是波浪式扩散的。

3. **决策维度：黄金4小时最优资源分配** — 不只说"加固10条路"，算"震后黄金4小时，有限的救援力量怎么分配才能最大限度延缓崩溃"。先修哪条路、先派哪个医疗队、先疏散哪个区 — 这是一个优化问题，不是建议列表。

### 8.3 范式升级

- 现在：算一次地震合肥会怎样 → 一份数据分析作业
- 以后：建模城市生命线在震后72小时如何逐步崩溃，找出延缓崩溃的最优干预 → 一个有决策价值的研究
- 别人算的是"地震那一刻城市怎样"，我们算的是"城市如何被拖垮、怎么延缓这个过程"

### 8.4 待确认

- 以上方向是否足够贴近"大数据实践赛"要求
- 大数据特征如何体现（数据规模？数据多样性？数据处理深度？）
- 需要研究比赛要求和获奖案例后确认

| 维度 | 获奖作品共性 | 常见失败原因 |
|------|------------|------------|

历届大数据主题赛题目：2021国家规划、2022新冠疫情、2023气候变化、2024乡村振兴、2025科技创新——**全是"用数据解读宏大社会议题"**。

### 9.3 我们项目的根本问题（视角太低）

| 层面 | 获奖作品 | 我们现状 | 差距 |
|------|---------|---------|------|
| 问题格局 | 用数据解读国家战略/全球议题 | 算合肥一个城市一次地震 | 格局差一个层级 |

**核心问题：项目本质是"一个假设性灾害场景的损失评估"，而大数据赛要的是"用数据驱动的社会洞察与决策支持"。**

## 十、项目立意升级：城市底线债务诊断（2026-07-27 讨论）

> 本次讨论是项目方向的关键转折。从"地震损失评估工具"升级到"城市底线债务诊断"，明确了项目的核心立意、价值主张、展现形态。

### 10.1 核心立意：城市发展留下了看不见的底线债务

**项目一句话：城市发展留下了看不见的底线债务，我们用数据把它算出来。**

"底线债务"的含义：
- 老城区道路老化、消防站不足——这是欠的债
- 新城区医院稀疏、资源分散——这也是欠的债
- 新老城交界处规划脱节——这还是债
- 这些债平时看不见，城市运转正常，但一旦有压力（地震、暴雨、疫情）就还不上了

**地震不是项目的主题。地震是检验这些债的手段。** 就像体检时的压力测试——你平时心率正常，但跑个步才知道心脏有没有问题。

这与之前"M5.5会崩"的定位有本质区别：
- 之前：算一个假设性灾害场景的损失
- 现在：揭示城市发展模式遗留的结构性脆弱，灾害只是放大镜

### 10.2 政府的盲区 = 我们的价值

**核心洞察：政府专业人士不是做不到，是组织方式决定了他们做不到。**

政府工作方式：
- 卫健委管医院，交通局管道路，应急局管救援，消防管消防
- 每个部门对自己的系统很专业，但部门之间是**割裂**的
- 没有一个部门负责"医疗依赖交通、救援依赖交通、避难依赖医疗+救援"这种**跨系统依赖关系**

这个割裂造成的盲区：
- 交通局知道哪条路会断，但不知道断了之后哪几家医院失救
- 卫健委知道医院可达性，但不知道救援系统崩了之后医疗会怎么被拖垮
- 应急局做预案，但预案是"各系统各自保运转"，没有"系统间级联崩溃"的概念

**这个盲区，传统方法填补不了：**
- 政府评估靠专家经验 + 单系统指标，没有跨系统拓扑建模的工具
- 商业公司能做但不开源、成本高、不会给地方政府用
- 地震科研机构做的是地震危险性，不是城市生命线系统脆弱性

**"为什么别人做不了"的答案：** 不是技术多高深，是这个**跨系统拓扑视角**没人用数据化的方式做。政府部门分割做不到，科研机构不关注，商业公司不公开。

### 10.3 为什么是我们能做

| 能力 | 我们有 | 政府专家没有 |
|------|--------|-------------|
| 图论/复杂网络建模 | 编程能实现 | 不是他们的工具箱 |
| 多源大数据融合 | 有技术能力 | 部门数据不互通 |
| 快速压力测试推演 | 秒级交互 | 他们做一次评估要数月 |
| 客观数据诊断 | 数据说话 | 经验主观 |

**学生身份反而是优势**：我们不受部门利益约束，可以跨系统看问题；我们没有"专业包袱"，敢于用新方法（复杂网络、蒙特卡洛）。

### 10.4 格局问题：不做全国，不做单城

**方法论 + 案例验证：**
- **合肥做深**：58K路段、426医院、46K网格，数据已就绪，做成完整验证案例
- **迁移性证明**：选郯庐带上的另一个城市，用同样的方法跑一遍，证明这套方法不是只能用于合肥
- **格局落在方法论上**：项目产出是"城市生命线底线诊断方法"，合肥是验证案例，不是研究对象本身

这样既不笼统（有具体案例），格局又够（方法论可迁移）。

### 10.5 新形态大数据创新点

不是传统"数据量大、来源多"的大数据。是**数据驱动的系统认知**。

| 传统大数据 | 我们的新形态 |
|-----------|-------------|
| 统计相关性 | 因果穿透（拓扑依赖链） |
| 指标堆砌 | 系统崩溃临界点识别 |
| 描述性分析 | 压力测试推演 |
| 单系统优化 | 跨系统级联失效建模 |
| 静态报告 | 交互式诊断工具 |

**核心创新：用大数据把城市理解为一个复杂系统，而不是一堆孤立指标的集合。** 这才是大数据的深度用法——不是数据多，是用数据看见传统方法看不见的系统结构。

### 10.6 立项表述

**完整版：**
> 城市生命线底线诊断——基于复杂网络与压力测试的城市系统脆弱性识别方法
>
> 以郯庐断裂带沿线城市为验证案例，用多源大数据建模城市生命线系统间的拓扑依赖关系，通过地震压力测试识别系统崩溃临界点与级联传播路径，为城市韧性规划提供跨系统视角的诊断工具。

**一句话版**：用大数据算出城市生命线"在哪崩、为什么崩、怎么延缓崩"——填补政府跨系统评估的盲区。

### 10.7 诊断而非解决方案：能力边界确认

**关键定位：我们做诊断工具，不做解决方案。**

- 纯风险展示（"合肥在M5.5会崩"）——价值低，政府不需要学生告诉他们有地震风险
- 纯解决方案（"加固这10条路"）——不可信，我们没有城市规划的专业资质
- **诊断工具**——不替政府做决策，而是给他们一个用数据看清楚问题的工具

类比：我们不是开药方的医生，而是做CT扫描的设备。医生（政府专家）用我们的扫描结果，结合他们的专业判断来做决策。

这个定位的优势：
- 符合比赛要求（大数据实践赛要"数据驱动决策支持"，不是"数据驱动决策"）
- 避开能力短板（不需要城市规划专业知识，只需要数据分析能力）
- 体现创新点（"底线识别"本身就是诊断方法，不是解决方案）
- 政府标准化（政府用的决策支持系统都是这个逻辑：给工具不给答案）

### 10.8 展现形态的反思与确认

**被否决的方向：**
- 纯拓扑诊断器（四个圆圈的依赖图）——太抽象，脱离真实城市
- 单页图表大屏——信息过载，没有故事
- PPT式网页——往下翻看数据，被动接收

**确认的方向：地图是主体，但地图要讲故事**

地图大屏方向没错，错的是地图上展示了什么。深度不在于把地图换掉，而在于让地图讲出别人讲不出的故事。

**展现的四个层次：**

1. **发现债务**：打开网页，先看到合肥的城市空间格局。地图上能看出：老城区医院密但路窄，新城区路宽但医院少，新老城交界处资源断层。这一层回答"城市欠了什么债"。

2. **压力施放，债务暴露**：施加地震压力，看哪些债先还不上了。不是简单地"医疗崩了"，而是"老城区因为路窄先断了，导致密集的医院反而先失救"——这种反直觉的发现才有深度。

3. **穿透根源**：为什么这里先崩？点开一个崩溃区域，看到的是：这个区老城比例高、路网老化、消防站覆盖不足——这是规划历史遗留的债，不是地震本身的问题。

4. **偿还策略**：加固哪些路、在哪里增建消防站，能把底线推高。但也要展示：有些债短期还不上（老城区没法拆了重建），只能靠区域协调来补。

**关键区别——信息节奏：** 不是一次全展示，而是按"正常→施压→崩溃→因果→解决"的顺序展开。地图上同一时刻只突出一个重点，用户跟着节奏理解整个发现。

### 10.9 算法层面的核心升级：跨系统依赖建模

**当前算法的根本缺陷（已确认）：**
现有 `step10_collapse_threshold.py` 的逻辑是四个系统各算各的，互不影响。医疗崩了不影响救援，交通崩了不影响医疗。这不真实。

**需要补的核心：系统间依赖关系**
- 交通崩了 → 沿依赖边传染给医疗（医疗靠路运物资）
- 医疗崩了 → 沿依赖边传染给避难（避难靠医疗转运伤员）
- 救援崩了 → 沿依赖边传染给避难（危险源失控）

依赖边的权重来自真实数据：医疗对交通的依赖度 = 依赖受损路网的医院占比（从已有的可达性矩阵推导）。

**这是算法层面的事，不影响"做出来的东西"是什么。** 用户看的是地图上崩溃的空间扩散过程，不是四个圆圈的拓扑图。
