## 一、架构决策

### 1.1 取消后端，改为纯前端架构

**原方案：** Python FastAPI 后端 + 前端调用 API

**新方案：** Python 预计算脚本 → 导出 JSON → 纯前端加载展示

**原因：**
- 所有分析结果已预计算完成（可达性、损失估算、灾害链等 CSV 已生成）
- 前端直接加载 JSON 即可展示，无需实时计算
- 部署简单（静态托管），加载快，展示时不依赖服务器更稳定
- 符合团队 HTML/CSS/JS 单文件 H5 开发的技术栈

### 1.2 技术栈

- 纯 HTML / CSS / JavaScript（单文件 H5）
- 高德地图 JS API（地图渲染，第一版已接入）
- ECharts（数据可视化组件）
- 数据源：预计算 JSON 文件

## 二、视觉呈现改动

### 2.1 放弃深色科技大屏

**问题：**
- 信息可读性差 — 深色背景上图表对比度低，数据辨识困难
- 装饰大于信息 — 发光边框、粒子动画、3D 效果抢数据的注意力
- 模板化严重 — 网上泛滥，一眼就是模板生成，AI 味太浓
- 不符合专业调性 — 大数据实践赛评的是数据处理和分析能力，不是炫技

### 2.2 改为浅色专业数据可视化大屏

**参考方向：** USGS 地震可视化、FT.com 数据新闻、Tableau Public 精品仪表板

**核心原则：**
- 信息密度优先 — 每寸屏幕都承载数据
- 浅色专业背景 — 图表清晰可读
- 语义化配色 — 基于地震烈度和风险等级（USGS 地震烈度色阶：浅黄→深红）
- 五步叙事流贯穿交互

### 2.3 五步叙事流

1. 空间错配 → 展示地震风险区与社会经济分布的空间不匹配
2. 压力施加 → 切换震级场景，施加地震压力
3. 脆弱性识别 → 识别道路阻断、医院不可达等脆弱点
4. 方案测试 → 级联灾害链分析，识别瓶颈
5. 损失防治建议 → 韧性指数评估，给出优化策略

### 3.2 各区域说明

| 区域 | 位置 | 内容 | 作用 |
|------|------|------|------|
| 顶部栏 | 全宽 | 项目标题 + 震级切换按钮组 | 全局入口，切换震级联动全屏数据 |
| 左侧 | 窄列 | 4 个 KPI 指标卡片 | 一眼掌握全局（人口/GDP/医院/道路） |
| 中央 | 主区域 | 高德地图多图层 | 信息密度最高的主视图，叠加 5 个图层 |
| 右侧 | 窄列 | 3 个辅助图表 | 补充地图无法展示的分析维度 |
| 底部 | 4 等分 | 4 个深度图表 | 展示分析深度（灾害链/韧性/对比/曲线） |

### 3.3 交互流程

切换震级 → 观察地图变化 → 查看 KPI 指标 → 深入底部分析

### 3.4 地图图层（中央主视图）

1. 烈度分布 — USGS 烈度色阶填充
2. 人口热力 — 人口密度热力图
3. 医院点位 — 按可达性状态着色（正常/受限/不可达）
4. 道路网络 — 按阻断等级着色（完全阻断/严重损伤/轻度损伤）
5. 灾害链节点 — 级联失效关键节点标注

### 3.5 配色方案

- 背景：浅灰白（#F5F7FA）
- 卡片：纯白（#FFFFFF）
- 烈度色阶：浅黄（#FFF3CD）→ 深红（#E03131），遵循 USGS 标准
- 强调色：蓝色（#2E86AB）用于品牌/数据系列
- 风险色：红色（#E74C3C）用于风险/阻断标记

## 四、项目核心定位

### 4.1 项目到底做什么

**用大数据算清楚"合肥在地震面前有多脆弱"，找到城市生命线系统崩溃的临界点。**

不是单纯算经济损失，也不是单纯算人口伤亡，而是算"城市生命线系统在几级地震下崩溃"。"城域底线"的"底线"是**功能底线**——城市还能不能运转的临界点。

### 4.2 四层逻辑链

1. **致灾层** — 地震在空间上施加了什么压力（烈度场、断裂带）
2. **承灾层** — 什么暴露在风险下（人口、GDP、医院、消防、避难所、危险源）
3. **脆弱性层** — 地震压力下各系统如何失效（道路阻断、可达性、级联灾害链）
4. **影响层** — 崩溃后的后果量化（人口影响、经济损失、韧性指数、防治建议）

### 4.3 损失三层结构

| 层次 | 内容 | 定位 |
|------|------|------|
| 系统崩溃（核心） | 医疗/救援/交通/避难四系统何时失效 | 项目创新点，评分重点 |
| 人口影响（支撑） | 各烈度区暴露人口、需转移人数 | 证明崩溃后果的严重性 |
| 经济损失（背景） | GDP 暴露量、建筑损毁估算 | 补充维度，不是主角 |

## 五、数据现状与问题

### 5.1 已完备的数据（无需改动）

- 烈度衰减场（500m 网格 × 6 震级，46K 网格）
- 断裂带缓冲区（10/30/50km 三级）
- 医院 426 家（真实高德 POI）
- 道路网络 58K 路段 × 6 震级阻断分级
- 医院可达性（NetworkX 图论计算）

### 5.2 模拟数据需补强

当前消防站 20 个、避难所 10 个、危险源 15 个均为随机生成的模拟数据。
- 问题：位置不合理，与真实城市布局脱节
- 方案：爬取真实 POI，或至少用合理分布逻辑（如消防站按消防辖区分布）

### 5.3 缺失数据需补充

- **人口/GDP 空间分布** — 当前仅有 9 区县汇总，需用 NPP-VIIRS 夜间灯光数据细化到网格级
- **影响层完全缺失** — 当前"损失估算"逻辑为 `医院数 × 损失率`，无物理意义，需重写
- **崩溃临界点识别** — 核心创新点，尚未实现

- [ ] **重写损失计算** — 用网格人口×烈度→暴露人口，用 GDP×损失率→经济损失，替换当前"医院数×损失率"的无意义算法

  - 医疗系统：可达医院比例低于 30% = 崩溃

## 七、比赛定位与创新点分析

### 7.1 比赛要求

大数据应用赛分两个子赛道：主题赛是命题的（2026 年是健康数据/电商/智能体），**实践赛是自主命题**——自带数据集、自主选题、自主开发。

实践赛提交材料：作品设计报告、源码及部署包、Web 应用展示视频、自建数据集。

报告模板要求覆盖：问题描述（来源/现有方案/痛点/解决思路）、技术方案、系统实现、系统评测。

国赛现场是 10 分钟汇报 + 10 分钟答辩，评委核心关注三点：**最大创新点、数据来源可靠性、技术方法科学性**。

### 7.2 三个创新点

| 创新点 | 别人怎么做 | 我们怎么做 | 状态 |
|--------|-----------|-----------|------|
| 空间错配量化 | 定性说"有风险" | 网格级量化风险与经济暴露的相关性 | 数据有，需补灯光数据 |
| 级联失效瓶颈 | 单点损失估算 | 图论路网分析 + 连锁崩溃链 | 基础有，需统一算法 |
| **崩溃临界点** | 算"损失多少" | **算"什么时候扛不住"** | **核心创新，尚未实现** |

### 7.3 核心差异化

第三个创新点是杀手锏。评委问"创新点在哪"，答案是：**"传统灾害分析算的是损失量，我们算的是城市功能崩溃的临界震级——这是从'损失评估'到'底线识别'的方法论升级。"**

### 7.4 项目意义

- **实践意义：** 告诉合肥城市管理者，城市在 M6.5 会出什么事，哪些路段必须先加固，哪些医院必须保通路，哪些危险源旁必须增设消防站。精确到"加固这 3 条路能把底线从 M6.0 推到 M6.5"。
- **方法意义：** 把地震灾害分析从"单点损失估算"升级到"系统崩溃临界点识别"。可迁移到任何城市的任何灾害类型。
- **比赛意义：** 大数据实践赛要的是数据驱动的洞见。每一步都有数据支撑，每一步都有可视化呈现。

### 7.5 获奖路径

| 门槛 | 需要完成 | 当前完成度 |
|------|---------|-----------|
| 省赛入围 | 完整大屏 + 基础损失计算 + 数据报告 | ~60% |
| 国赛入围 | 崩溃临界点识别 + 重写损失算法 + 统一可达性 + 专业大屏 | ~45% |
| 国赛一等奖 | 夜间灯光数据 + 防治策略推演 + 答辩无盲区 + 报告少而精 | ~30% |
